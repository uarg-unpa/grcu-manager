CU-14: Validar requerimiento

Descripción
Permite validar un requerimiento dentro de un proyecto, asegurando que cumple con los criterios de aceptación definidos y que ha sido revisado por los roles autorizados. La validación puede implicar la aprobación formal (metodología tradicional) o la aceptación por parte del stakeholder (metodología ágil). El proceso queda registrado en el sistema de auditoría para trazabilidad.

Actores
- Líder del proyecto (puede validar requerimientos)
- Stakeholder (puede validar requerimientos en metodología ágil)
- Desarrollador (consulta estado de validación)

Precondiciones
- Usuario autenticado con permisos de validación en el proyecto
- Requerimiento existente y activo
- Criterios de aceptación definidos (según metodología)

Postcondiciones
- Estado del requerimiento actualizado a "Validado" o equivalente
- Registro de validación en auditoria_registroactividad
- Cambios reflejados en listados y reportes

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. Selecciona el requerimiento a validar
3. Hace clic en "Validar requerimiento"
4. El sistema verifica permisos y criterios de aceptación
5. El sistema muestra formulario de validación (puede incluir comentarios, adjuntos, criterios)
6. El usuario confirma la validación
7. El sistema actualiza el estado del requerimiento a "Validado"
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito: "Requerimiento validado correctamente"
10. El sistema recarga la vista con el nuevo estado

Flujos Alternativos
A1. Usuario sin permisos de validación
- El sistema bloquea la acción y muestra mensaje: "No tienes permisos para validar este requerimiento"
- Registra intento en log de seguridad

A2. Requerimiento ya validado
- El sistema detecta estado "Validado"
- Muestra mensaje: "Este requerimiento ya ha sido validado"
- No permite validar nuevamente

A3. Criterios de aceptación incompletos
- El sistema detecta que faltan criterios
- Muestra mensaje: "No se puede validar el requerimiento: faltan criterios de aceptación"
- Permite volver y completar criterios

A4. Error al registrar validación
- El sistema captura la excepción
- Muestra mensaje: "Error al validar el requerimiento, intente nuevamente"
- Registra el error en logs

Reglas de Negocio
- RN-01: Solo Líder y Stakeholder pueden validar requerimientos
- RN-02: Un requerimiento solo puede validarse si cumple criterios de aceptación
- RN-03: La validación se registra en auditoría con detalles completos
- RN-04: No se puede validar dos veces el mismo requerimiento
- RN-05: El estado "Validado" es visible en listados y reportes

Estado de Implementación
✅ IMPLEMENTADO
- Vista de validación en requerimientos/views.py
- Permisos y validaciones en modelos y vistas
- Registro en auditoría
- Estado reflejado en listados

Prioridad
ALTA - Clave para control de calidad y avance del proyecto

CU-09: Consultar historial de caso de uso

Descripción
Permite a los usuarios consultar el historial completo de cambios realizados sobre un caso de uso específico dentro de un proyecto. El historial incluye modificaciones en campos, cambios de estado, vinculaciones/desvinculaciones con requerimientos, adjuntos, comentarios y toda la trazabilidad relevante. Esta funcionalidad es clave para auditoría, análisis retrospectivo y control de calidad.

Actores
- Líder del proyecto (acceso completo al historial)
- Analista/Desarrollador (visualiza historial de casos de uso que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Caso de uso existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el caso de uso

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el caso de uso ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
    accion = CONSULTA_HISTORIAL_CASODEUSO
    detalles (JSON) = {casodeuso_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de casos de uso del proyecto
2. Selecciona un caso de uso específico
3. Hace clic en "Ver detalle" o accede directamente a la vista del caso de uso
4. El sistema muestra la pantalla de detalle del caso de uso con pestañas/secciones:
    - Información actual
    - Requerimientos relacionados
    - Adjuntos
    - Comentarios
    - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del caso de uso:
    - Desde casos_de_uso_historicalcasodeuso (django-simple-history)
    - Incluye cambios en detalles tradicionales/ágiles
    - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
    - Botón "Ver detalles" para expandir
9. El usuario puede:
    - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

- Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
- El sistema detecta ausencia de módulo de auditoría
- Muestra mensaje: "El historial de cambios no está disponible en este momento"
- Muestra solo: fecha de creación, creado por, fecha de última actualización
- Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
- El sistema detecta historial extenso
- Muestra paginación y filtros avanzados
- Permite exportar historial a archivo (CSV/PDF)

Reglas de Negocio
- RN-01: Solo usuarios con permisos en el proyecto pueden consultar el historial
- RN-02: El historial debe mostrar todos los cambios relevantes, incluyendo vinculaciones y comentarios
- RN-03: El registro en auditoría es obligatorio para trazabilidad
- RN-04: La consulta del historial no modifica datos
- RN-05: El historial debe ser accesible desde la vista de detalle del caso de uso

Estado de Implementación
✅ IMPLEMENTADO
- Vista de historial en casos_de_uso/views.py

CU-10: Registrar caso de uso

Descripción
Permite crear un nuevo caso de uso en el proyecto, especificando sus características según la metodología definida (Tradicional o Ágil). El caso de uso describe una funcionalidad, proceso o interacción relevante para el sistema, y puede estar vinculado a uno o más requerimientos.

Actores
- Analista
- Líder del proyecto
- Desarrollador

Precondiciones
- Usuario autenticado con permisos de edición en el proyecto
- Proyecto existente y activo
- Metodología asignada al proyecto (Tradicional o Ágil)

Postcondiciones
- Caso de uso registrado en la base de datos (casos_de_uso_casodeuso)
- Detalles tradicionales o ágiles almacenados según metodología
- Caso de uso vinculado al proyecto y, opcionalmente, a requerimientos
- Registro de actividad en auditoría

Flujo Principal
1. El usuario accede a la sección "Casos de Uso" del proyecto
2. Hace clic en "Nuevo Caso de Uso"
3. El sistema muestra formulario con campos según metodología:
    - Tradicional: nombre, descripción, actor principal, precondiciones, flujo principal, flujo alternativo, postcondiciones, observaciones
    - Ágil: nombre, descripción, historia de usuario, criterio de aceptación, responsable, estado scrum, observaciones
    - Adjuntos: imagen, archivo, link externo (opcional)
    - Selección de requerimientos vinculados (opcional)
4. El usuario completa los campos obligatorios y opcionales
5. El sistema valida los datos:
    - Campos obligatorios completos
    - Formato de adjuntos y links
    - Permisos del usuario
6. El sistema guarda el caso de uso y sus detalles en la base de datos
7. El sistema vincula el caso de uso a los requerimientos seleccionados (si corresponde)
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito: "Caso de uso registrado correctamente"
10. El sistema redirige a la vista de detalle del caso de uso

Flujos Alternativos
A1. Proyecto sin metodología
- El sistema bloquea la creación y muestra mensaje: "Debes seleccionar Tradicional o Ágil antes de crear casos de uso"

A2. Campos obligatorios incompletos
- El sistema muestra mensaje de error y solicita corrección

A3. Error al guardar en base de datos
- El sistema muestra mensaje: "Error al guardar el caso de uso. Intenta nuevamente"
- Registra el error en logs

A4. Usuario sin permisos
- El sistema bloquea la acción y muestra mensaje de error

Reglas de Negocio
- RN-01: Solo usuarios con permisos de edición pueden crear casos de uso
- RN-02: Los campos obligatorios varían según metodología
- RN-03: Un caso de uso puede estar vinculado a varios requerimientos
- RN-04: Los adjuntos deben cumplir formato y tamaño permitido
- RN-05: El registro en auditoría es obligatorio

Estado de Implementación
✅ IMPLEMENTADO
- Vista de creación en casos_de_uso/views.py
- Formularios tradicionales y ágiles en casos_de_uso/forms.py
- Vinculación con requerimientos
- Registro en auditoría

Prioridad
ALTA - Fundamental para modelado funcional y trazabilidad

CU-00: Creación de usuario administrador inicial

Descripción
Al iniciarse el sistema por primera vez, se verifica el estado de la base de datos. Si no existe un usuario con rol de administrador registrado, el sistema solicita la creación de uno para completar el despliegue inicial mediante Google OAuth2.

El proceso de primer inicio ha sido simplificado con OAuth2:
- NO requiere formulario de registro: Google provee los datos
- Autenticación delegada: Google gestiona seguridad y credenciales
- Avatar automático: Se almacena URL del avatar de Google en accounts_usuario.avatar
- Email verificado: Google garantiza la verificación del email
- Proceso seguro: Sin manejo local de contraseñas

Una vez completada la autenticación OAuth2, el sistema:
1. Crea el usuario administrador inicial en accounts_usuario
2. Asigna automáticamente el rol "Admin" en usuarios_usuario_roles (M2M)
3. Almacena avatar URL de Google en campo avatar
4. Registra la actividad en auditoria_registroactividad con acción LOGIN
5. Habilita todas las funcionalidades de administración
6. Completa el despliegue inicial del sistema

Actores
- Instalador del sistema (primera ejecución, requiere cuenta Gmail)

Precondiciones
- Sistema desplegado en servidor/localhost
- Base de datos PostgreSQL inicializada con las 29 tablas
- Google OAuth2 configurado en settings.py:
   SOCIALACCOUNT_PROVIDERS['google']['APP']['client_id']
   SOCIALACCOUNT_PROVIDERS['google']['APP']['secret']
   URLs de redirección registradas en Google Cloud Console
- NO existe ningún usuario administrador en accounts_usuario
- Aplicación registrada en Google Cloud Console
- django-allauth instalado y configurado

Postcondiciones
- Usuario administrador creado en accounts_usuario con rol "Admin"
- Avatar URL almacenado en campo accounts_usuario.avatar
- Registro de LOGIN en auditoria_registroactividad con:
   usuario = admin recién creado
   accion = LOGIN
   detalles (JSON) = {"primer_acceso": true, "oauth_provider": "google"}
   ip_address = IP del instalador
   user_agent = navegador usado
- Sistema listo para uso colaborativo
- Posibilidad de crear nuevos usuarios, roles y proyectos

Flujo Principal (OAuth2)
1. El instalador accede a la URL del sistema (ej: http://localhost:8000/)
2. El sistema detecta ausencia de usuarios administradores en accounts_usuario
3. El sistema redirige a pantalla de primer acceso con mensaje:
   ``
   "Bienvenido al sistema GRCU Manager
   Para comenzar, inicia sesión con tu cuenta de Google"
   `
4. El sistema muestra botón "Iniciar sesión con Google" (único método disponible)
5. El instalador hace clic en "Iniciar sesión con Google"
6. El sistema redirige a Google OAuth2 (https://accounts.google.com/o/oauth2/v2/auth)
7. Google solicita al instalador:
   - Seleccionar cuenta de Gmail
   - Autorizar permisos: email, perfil, foto de perfil
8. El instalador selecciona cuenta y autoriza
9. Google redirige de vuelta al sistema con código de autorización
10. El sistema intercambia código por access token (backend)
11. El sistema obtiene datos del usuario de Google API:
    `json
    {
      "email": "admin@gmail.com",
      "name": "John Admin",
      "picture": "https://lh3.googleusercontent.com/a/...",
      "verified_email": true
    }
    `
12. El sistema crea usuario en accounts_usuario:
    `python
    usuario = Usuario.objects.create(
        email="admin@gmail.com",
        nombre="John Admin",
        avatar="https://lh3.googleusercontent.com/a/...",
        is_staff=True,
        is_superuser=True
    )
    `
13. El sistema asigna rol "Admin" en usuarios_usuario_roles (M2M)
14. El sistema registra actividad en auditoria_registroactividad:
    `python
    RegistroActividad.objects.create(
        usuario=usuario,
        accion='LOGIN',
        detalles={
            "primer_acceso": True,
            "oauth_provider": "google",
            "email": usuario.email
        },
        ip_address=request.META.get('REMOTE_ADDR'),
        user_agent=request.META.get('HTTP_USER_AGENT')
    )
    `
15. El sistema crea sesión en django_session
16. El sistema redirige al dashboard de administración (/dashboard/)
17. El sistema muestra mensaje de bienvenida:
    `
    "✅ Bienvenido, John Admin
    Eres el administrador inicial del sistema.
    Comienza creando tu primer proyecto."
    `
18. El instalador ve su avatar de Google en la navbar

Flujos Alternativos (OAuth2)

A1. Usuario cancela en pantalla de Google
1. El instalador hace clic en "Cancelar" o cierra la ventana de Google OAuth
2. Google redirige de vuelta al sistema con error
3. El sistema muestra mensaje: "Inicio de sesión cancelado. El sistema requiere autenticación con Google para crear el usuario administrador."
4. El sistema vuelve a mostrar botón "Iniciar sesión con Google"
5. Fin del caso de uso

A2. Google rechaza la autorización
1. Google detecta cuenta sospechosa o problema de seguridad
2. Google muestra error de autenticación
3. El sistema recibe error de OAuth
4. El sistema registra el error en logs
5. El sistema muestra mensaje: "Error de autenticación. Por favor, intenta con otra cuenta de Google o contacta al soporte."
6. Fin del caso de uso

A3. Error en intercambio de tokens
1. El sistema intenta intercambiar código por access token
2. La petición a Google falla (timeout, error de red, token inválido)
3. El sistema captura la excepción
4. El sistema registra error en logs con detalles técnicos
5. El sistema muestra mensaje: "Error técnico al procesar la autenticación. Intenta nuevamente."
6. El sistema vuelve a pantalla de primer acceso
7. Fin del caso de uso

A4. Ya existe un usuario administrador
1. Durante el proceso, otro instalador crea el primer admin simultáneamente
2. El sistema detecta que ya existe un usuario con rol Admin
3. El sistema cancela la creación del nuevo usuario
4. El sistema redirige a página de login normal
5. El sistema muestra mensaje: "El sistema ya tiene un administrador. Usa el login normal o contacta al administrador para obtener acceso."
6. Fin del caso de uso

Reglas de Negocio

- RN-01: El primer usuario creado DEBE tener rol "Admin" automáticamente
- RN-02: Solo se permite UN proceso de creación de administrador inicial
- RN-03: La autenticación DEBE ser exclusivamente mediante Google OAuth2
- RN-04: No se almacenan contraseñas localmente (Google gestiona credenciales)
- RN-05: El email de Google debe ser único en el sistema
- RN-06: El avatar URL se almacena tal como lo proporciona Google
- RN-07: Si falla OAuth, el sistema NO queda en estado inconsistente
- RN-08: El registro en auditoría es obligatorio para trazabilidad
- RN-09: La sesión se crea automáticamente tras autenticación exitosa

Estado de Implementación

✅ IMPLEMENTADO

El sistema OAuth2 con Google está completamente funcional:
- django-allauth configurado y operativo
- Flujo OAuth2 implementado en accounts/views.py
- Creación automática de usuario administrador
- Almacenamiento de avatar de Google
- Registro de auditoría en auditoria_registroactividad

CU-04: Asignar roles de usuario al proyecto

Descripción

El líder del proyecto gestiona los roles de los participantes asignados al proyecto. Esta funcionalidad permite:

- Asignar roles específicos a cada integrante según su función en el proyecto
- Modificar roles de integrantes existentes cuando cambian responsabilidades
- Diferenciar niveles de acceso según el rol asignado

Roles disponibles para asignar:
- Desarrollador: Puede crear y editar requerimientos y casos de uso
- Stakeholder (Cliente): Solo lectura, puede comentar y validar
- Visitante: Solo visualización sin permisos de modificación

Roles especiales (automáticos, no asignables):
- Líder: Se asigna automáticamente al crear el proyecto, solo uno por proyecto
- Admin: Rol de sistema, no puede asignarse a proyectos

El líder del proyecto es el único autorizado para modificar roles, excepto su propio rol que permanece como "Líder" mientras sea líder del proyecto.

Actores

- Líder del proyecto (único autorizado para gestionar roles)
- Participantes del proyecto (usuarios que reciben roles)

Precondiciones

- Usuario autenticado como líder del proyecto
- Proyecto existente con al menos un participante
- Los participantes están vinculados al proyecto mediante proyectos_participacionproyecto
- Usuario tiene acceso a /proyectos/{proyecto_id}/gestionar-integrantes/

Postcondiciones

- Roles actualizados en tabla proyectos_participacionproyecto
- Campo rol_id modificado para los usuarios seleccionados
- Cambios visibles inmediatamente en permisos de acceso
- Actividad registrada en auditoria_registroactividad:
  `python
  accion = 'MODIFICACION_ROL_PROYECTO'
  detalles = {
      "proyecto_id": proyecto.id,
      "proyecto_nombre": proyecto.nombre,
      "usuario_modificado": usuario.email,

@login_required
def gestionar_integrantes(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)
    
    # Validar que el usuario es el líder
    if proyecto.lider != request.user:
        messages.error(request, "No tienes permisos para gestionar integrantes.")
        return redirect('dashboards:lider_dashboard')
    
    # Obtener roles permitidos
    rol_desarrollador = get_object_or_404(Rol, nombre="Desarrollador")
    rol_stakeholder = get_object_or_404(Rol, nombre="Stakeholder")
    rol_visitante = get_object_or_404(Rol, nombre="Visitante")
    roles_permitidos = [rol_desarrollador, rol_stakeholder, rol_visitante]
    
    if request.method == 'POST':
        for key, value in request.POST.items():
            if key.startswith('rol_'):
                try:
                    usuario_id = int(key.split('_')[1])
                    nuevo_rol_id = int(value)
                    
                    usuario = proyecto.participantes.get(id=usuario_id)
                    nuevo_rol = Rol.objects.get(id=nuevo_rol_id)
                    
                    # Validar rol permitido
                    if nuevo_rol not in roles_permitidos:
                        messages.error(request, f"El rol {nuevo_rol.nombre} no está permitido.")
                        continue
                    
                    # No cambiar rol del líder
                    if usuario == proyecto.lider:
                        messages.warning(request, "No puedes cambiar tu propio rol como líder.")
                        continue
                    
                    # Actualizar participación
                    participacion, created = ParticipacionProyecto.objects.update_or_create(
                        usuario=usuario,
                        proyecto=proyecto,
                        defaults={'rol': nuevo_rol}
                    )
                    
                except (ValueError, Usuario.DoesNotExist, Rol.DoesNotExist):
                    continue
        
        messages.success(request, "Los roles han sido actualizados correctamente.")
        return redirect('proyectos:gestionar_integrantes', proyecto_id=proyecto_id)
    
    # Obtener participaciones actuales
    participaciones = ParticipacionProyecto.objects.filter(
        proyecto=proyecto
    ).select_related('usuario', 'rol')
    
    usuarios_con_roles = []
    for participante in proyecto.participantes.all():
        try:
            participacion = participaciones.get(usuario=participante)
            rol_actual = participacion.rol
        except ParticipacionProyecto.DoesNotExist:
            # Asignar rol por defecto
            rol_actual = rol_desarrollador
            ParticipacionProyecto.objects.create(
                usuario=participante,
                proyecto=proyecto,
                rol=rol_desarrollador
            )
        
        usuarios_con_roles.append({
            'usuario': participante,
            'rol_actual': rol_actual,
            'es_lider': participante == proyecto.lider,
        })
    
    context = {
        'proyecto': proyecto,
        'usuarios_con_roles': usuarios_con_roles,
        'roles_permitidos': roles_permitidos,
        'page_title': f'{proyecto.nombre} - Gestión de Integrantes',
    }
    
    return render(request, 'proyectos/gestionar_integrantes.html', context)

CU-05: Seleccionar metodología

Descripción

El líder del proyecto asigna la metodología de trabajo (Tradicional o Ágil) que se utilizará para gestionar los requerimientos del proyecto. Esta decisión es fundamental porque determina:

- Campos de requerimientos: Los requerimientos tendrán campos específicos según metodología
  - Tradicional: fuente, categoría, prioridad MoSCoW, fecha compromiso
  - Ágil: historia de usuario, criterios de aceptación, puntos estimados, sprint
- Flujo de trabajo: Proceso de validación y aprobación de requerimientos
- Reportes y métricas: Tipo de informes generados (burndown charts para ágil, Gantt para tradicional)
- Plantillas: Formatos de documentación y casos de uso

La metodología se asigna una sola vez al inicio del proyecto. Solo se puede cambiar si:
- NO hay requerimientos creados aún
- El líder tiene motivos justificados para el cambio

Una vez que existen requerimientos, la metodología queda bloqueada para mantener consistencia en los datos.

Actores

- Líder del proyecto (único autorizado para asignar/cambiar metodología)

Precondiciones

- Usuario autenticado como líder del proyecto
- Proyecto existente en estado activo
- Usuario es el líder asignado en proyectos_proyecto.lider
- El proyecto no tiene metodología asignada (metodologia IS NULL o metodologia = '')
  - O si ya tiene metodología, NO debe tener requerimientos creados

Postcondiciones

- Campo metodologia actualizado en proyectos_proyecto con valor 'TRADICIONAL' o 'AGIL'
- Proyecto habilitado para crear requerimientos con campos específicos de la metodología
- Cambio registrado en proyectos_historicalproyecto (django-simple-history)
- Actividad registrada en auditoria_registroactividad:

CU-11: Definir dependencias

Descripción
Permite vincular requerimientos y casos de uso entre sí para establecer relaciones de dependencia, trazabilidad y cobertura funcional. El objetivo es asegurar que cada requerimiento esté respaldado por uno o más casos de uso y que los casos de uso respondan a necesidades reales del proyecto.

Actores
- Analista
- Desarrollador
- Líder del proyecto

Precondiciones
- Proyecto existente con requerimientos y casos de uso registrados
- Usuario autenticado con permisos de edición en el proyecto

Postcondiciones
- Dependencias registradas en la base de datos (tabla intermedia RequerimientoCaso)
- Matriz de trazabilidad actualizada
- Relación visible en las vistas de detalle de requerimiento y caso de uso
- Registro de actividad en auditoría

Flujo Principal
1. El usuario accede al detalle de un requerimiento o caso de uso
2. Hace clic en "Relacionar casos de uso" o "Relacionar requerimientos"
3. El sistema muestra lista de elementos disponibles para vincular (solo del mismo proyecto)
4. El usuario selecciona uno o más elementos y confirma
5. El sistema valida que la relación no exista previamente
6. El sistema crea la relación en la tabla intermedia
7. El sistema actualiza la matriz de trazabilidad
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito y actualiza la vista

Flujos Alternativos
A1. Relación ya existente
- El sistema detecta que la dependencia ya existe y muestra mensaje informativo

A2. Usuario sin permisos
- El sistema bloquea la acción y muestra mensaje de error

A3. Proyecto sin elementos disponibles
- El sistema muestra mensaje: "No hay elementos disponibles para relacionar"

Reglas de Negocio
- RN-01: Solo se pueden vincular elementos del mismo proyecto
- RN-02: Un requerimiento puede estar vinculado a varios casos de uso y viceversa
- RN-03: No se permite duplicar relaciones

@login_required
def gestionar_integrantes(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)
    
    # Validar que el usuario es el líder
    if proyecto.lider != request.user:
        messages.error(request, "No tienes permisos para gestionar integrantes.")
        return redirect('dashboards:lider_dashboard')
    
    # Obtener roles permitidos
    rol_desarrollador = get_object_or_404(Rol, nombre="Desarrollador")
    rol_stakeholder = get_object_or_404(Rol, nombre="Stakeholder")
    rol_visitante = get_object_or_404(Rol, nombre="Visitante")
    roles_permitidos = [rol_desarrollador, rol_stakeholder, rol_visitante]
    
    if request.method == 'POST':
        for key, value in request.POST.items():
            if key.startswith('rol_'):
                try:
                    usuario_id = int(key.split('_')[1])
                    nuevo_rol_id = int(value)
                    
                    usuario = proyecto.participantes.get(id=usuario_id)
                    nuevo_rol = Rol.objects.get(id=nuevo_rol_id)
                    
                    # Validar rol permitido
                    if nuevo_rol not in roles_permitidos:
                        messages.error(request, f"El rol {nuevo_rol.nombre} no está permitido.")
                        continue
                    
                    # No cambiar rol del líder
                    if usuario == proyecto.lider:
                        messages.warning(request, "No puedes cambiar tu propio rol como líder.")
                        continue
                    
                    # Actualizar participación
                    participacion, created = ParticipacionProyecto.objects.update_or_create(
                        usuario=usuario,
                        proyecto=proyecto,
                        defaults={'rol': nuevo_rol}
                    )
                    
                except (ValueError, Usuario.DoesNotExist, Rol.DoesNotExist):
                    continue
        
        messages.success(request, "Los roles han sido actualizados correctamente.")
        return redirect('proyectos:gestionar_integrantes', proyecto_id=proyecto_id)
    
    # Obtener participaciones actuales
    participaciones = ParticipacionProyecto.objects.filter(
        proyecto=proyecto
    ).select_related('usuario', 'rol')
    
    usuarios_con_roles = []
    for participante in proyecto.participantes.all():
        try:
            participacion = participaciones.get(usuario=participante)
            rol_actual = participacion.rol
        except ParticipacionProyecto.DoesNotExist:
            # Asignar rol por defecto
            rol_actual = rol_desarrollador
            ParticipacionProyecto.objects.create(
                usuario=participante,
                proyecto=proyecto,
                rol=rol_desarrollador
            )
        
        usuarios_con_roles.append({
            'usuario': participante,
            'rol_actual': rol_actual,
            'es_lider': participante == proyecto.lider,
        })
    
    context = {
        'proyecto': proyecto,
        'usuarios_con_roles': usuarios_con_roles,
        'roles_permitidos': roles_permitidos,
        'page_title': f'{proyecto.nombre} - Gestión de Integrantes',
    }
    
    return render(request, 'proyectos/gestionar_integrantes.html', context)

CU-05: Seleccionar metodología

Descripción

Descripción

@login_required
def gestionar_integrantes(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)
    
    # Validar que el usuario es el líder
    if proyecto.lider != request.user:
        messages.error(request, "No tienes permisos para gestionar integrantes.")
        return redirect('dashboards:lider_dashboard')
    
    # Obtener roles permitidos
    rol_desarrollador = get_object_or_404(Rol, nombre="Desarrollador")
    rol_stakeholder = get_object_or_404(Rol, nombre="Stakeholder")
    rol_visitante = get_object_or_404(Rol, nombre="Visitante")
    roles_permitidos = [rol_desarrollador, rol_stakeholder, rol_visitante]
    
    if request.method == 'POST':
        for key, value in request.POST.items():
            if key.startswith('rol_'):
                try:
                    usuario_id = int(key.split('_')[1])
                    nuevo_rol_id = int(value)
                    
                    usuario = proyecto.participantes.get(id=usuario_id)
                    nuevo_rol = Rol.objects.get(id=nuevo_rol_id)
                    
                    # Validar rol permitido
                    if nuevo_rol not in roles_permitidos:
                        messages.error(request, f"El rol {nuevo_rol.nombre} no está permitido.")
                        continue
                    
                    # No cambiar rol del líder
                    if usuario == proyecto.lider:
                        messages.warning(request, "No puedes cambiar tu propio rol como líder.")
                        continue
                    
                    # Actualizar participación
                    participacion, created = ParticipacionProyecto.objects.update_or_create(
                        usuario=usuario,
                        proyecto=proyecto,
                        defaults={'rol': nuevo_rol}
                    )
                    
                except (ValueError, Usuario.DoesNotExist, Rol.DoesNotExist):
                    continue
        
        messages.success(request, "Los roles han sido actualizados correctamente.")
        return redirect('proyectos:gestionar_integrantes', proyecto_id=proyecto_id)
    
    # Obtener participaciones actuales
    participaciones = ParticipacionProyecto.objects.filter(
        proyecto=proyecto
    ).select_related('usuario', 'rol')
    
    usuarios_con_roles = []
    for participante in proyecto.participantes.all():
        try:
            participacion = participaciones.get(usuario=participante)
            rol_actual = participacion.rol
        except ParticipacionProyecto.DoesNotExist:
            # Asignar rol por defecto
            rol_actual = rol_desarrollador
            ParticipacionProyecto.objects.create(
                usuario=participante,
                proyecto=proyecto,
                rol=rol_desarrollador
            )
        
        usuarios_con_roles.append({
            'usuario': participante,
            'rol_actual': rol_actual,
            'es_lider': participante == proyecto.lider,
        })
    
    context = {
        'proyecto': proyecto,
        'usuarios_con_roles': usuarios_con_roles,
        'roles_permitidos': roles_permitidos,
        'page_title': f'{proyecto.nombre} - Gestión de Integrantes',
    }
    
    return render(request, 'proyectos/gestionar_integrantes.html', context)

CU-05: Seleccionar metodología

Descripción

El líder del proyecto asigna la metodología de trabajo (Tradicional o Ágil) que se utilizará para gestionar los requerimientos del proyecto. Esta decisión es fundamental porque determina:

- Campos de requerimientos: Los requerimientos tendrán campos específicos según metodología

  - Ágil: historia de usuario, criterios de aceptación, puntos estimados, sprint

- NO hay requerimientos creados aún

Actores
- Analista
- Desarrollador
- Líder del proyecto

CU-08: Consultar historial de requerimientos

Descripción
Los usuarios con permisos adecuados pueden consultar el historial completo de cambios realizados sobre un requerimiento específico.

El historial incluye:
- Cambios de estado: Pendiente → En progreso → Completado
- Modificaciones de campos: nombre, descripción, tipo, prioridad
- Cambios en detalles específicos: campos tradicionales/ágiles
- Vinculaciones/desvinculaciones con casos de uso
- Adjuntos agregados o eliminados
- Comentarios registrados
- Metadatos: quién realizó el cambio, cuándo, desde qué IP (opcional)

Cada entrada del historial muestra:
- Fecha y hora del cambio
- Usuario que realizó la modificación
- Tipo de cambio (creación, edición, cambio de estado, etc.)
- Valores anteriores y nuevos (para campos modificados)
- Comentario opcional sobre el motivo del cambio

Este registro es fundamental para:
- Auditoría y cumplimiento normativo
- Trazabilidad de decisiones
- Resolución de conflictos
- Análisis retrospectivo

Actores
- Líder del proyecto (acceso completo al historial)
- Desarrollador/Analista (visualiza historial de requerimientos que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Requerimiento existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el requerimiento

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el requerimiento ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
   accion = CONSULTA_HISTORIAL
   detalles (JSON) = {requerimiento_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. El usuario selecciona un requerimiento específico
3. El usuario hace clic en "Ver detalle" o accede directamente a la vista de requerimiento
4. El sistema muestra la pantalla de detalle del requerimiento con pestañas/secciones:
   - Información actual
   - Casos de uso relacionados
   - Adjuntos
   - Comentarios
   - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del requerimiento:
   - Desde requerimientos_historicalrequerimiento (django-simple-history)
   - Incluye cambios en detalles: requerimientos_historicaldetallerequerimientotradicional o requerimientos_historicaldetallerequerimientoagil
   - Complementa con registros de auditoria_registroactividad para ver acciones específicas
7. El sistema combina datos de ambas fuentes:
   - django-simple-history: Snapshots completos de cada versión del requerimiento
   - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
   - Fecha y hora del cambio
   - Avatar/nombre del usuario que realizó el cambio
   - Icono según tipo de acción (creación, edición, cambio de estado, etc.)
   - Descripción del cambio en lenguaje natural
   - Botón "Ver detalles" para expandir
9. El usuario puede:
   - Revisar la lista completa de cambios
   - Expandir una entrada para ver detalles campo por campo
   - Comparar dos versiones específicas
   - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
11. El sistema muestra un modal/panel expandido con:
    - Tabla comparativa "Antes → Después"
    - Campos modificados destacados
    - Valores anteriores y nuevos
    - Comentario del usuario (si existe)
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

Flujos Alternativos

A1. Requerimiento sin historial (recién creado)
1. El sistema detecta solo la versión inicial
2. El sistema muestra mensaje: "Este requerimiento no tiene historial de cambios aún"
3. Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
1. El sistema detecta ausencia de módulo de auditoría
2. El sistema muestra mensaje: "El historial de cambios no está disponible en este momento"
3. Muestra solo: fecha de creación, creado por, fecha de última actualización
4. Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
1. El sistema detecta que participaciones.count() == 0
2. El sistema muestra mensaje:
   `
   ℹ️ Este proyecto no tiene participantes asignados.
   
   Para agregar participantes:
   1. Asigna un grupo al proyecto en "Editar Proyecto"
   2. O contacta al administrador para agregar usuarios manualmente
   
   [Volver al Dashboard]
   `
3. No se muestra la tabla de gestión
4. Fin del caso de uso

A4. Rol inválido seleccionado
1. El sistema recibe un rol_id no permitido en paso 12
2. El sistema valida: nuevo_rol not in roles_permitidos
3. El sistema omite ese cambio y muestra error:
   `
   ❌ El rol seleccionado para Juan Pérez no está permitido.
   Los demás cambios se guardaron correctamente.
   `
4. Los cambios válidos se guardan normalmente

A5. Usuario ya no es participante del proyecto

`python
@login_required
def asignar_metodologia(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)
    
    # Verificar que el usuario sea el líder
    if proyecto.lider != request.user:
        messages.error(request, "Solo el líder puede asignar la metodología.")
        return redirect("dashboards:lider_dashboard")
    
    # Verificar si se puede cambiar
    if not proyecto.necesita_metodologia() and not proyecto.puede_cambiar_metodologia():
        messages.error(request, "No puedes cambiar la metodología porque ya tiene requerimientos.")
        return redirect("dashboards:lider_dashboard")
    
    if request.method == "POST":
        metodologia = request.POST.get('metodologia')
        
        if metodologia in ['TRADICIONAL', 'AGIL']:
            proyecto.metodologia = metodologia
            proyecto.save()
            
            # Registrar en auditoría
            RegistroActividad.objects.create(
                usuario=request.user,
                accion='ASIGNACION_METODOLOGIA',
                detalles={
                    "proyecto_id": proyecto.id,
                    "proyecto_nombre": proyecto.nombre,
                    "metodologia": metodologia
                },
                ip_address=request.META.get('REMOTE_ADDR'),
                user_agent=request.META.get('HTTP_USER_AGENT')
            )
            
            metodologia_nombre = "Tradicional" if metodologia == "TRADICIONAL" else "Ágil"
            messages.success(request, f"Metodología '{metodologia_nombre}' asignada correctamente.")
            return redirect("dashboards:lider_dashboard")
        else:
            messages.error(request, "Metodología inválida seleccionada.")
    
    return render(request, "proyectos/asignar_metodologia.html", {
        "proyecto": proyecto,
        "puede_cambiar": proyecto.puede_cambiar_metodologia(),
        "necesita_metodologia": proyecto.necesita_metodologia(),
        "page_title": "Asignar Metodología"
    })

CU-11: Definir dependencias

Descripción
Permite vincular requerimientos y casos de uso entre sí para establecer relaciones de dependencia, trazabilidad y cobertura funcional. El objetivo es asegurar que cada requerimiento esté respaldado por uno o más casos de uso y que los casos de uso respondan a necesidades reales del proyecto.

Actores
- Analista
- Desarrollador
- Líder del proyecto

Precondiciones
- Proyecto existente con requerimientos y casos de uso registrados
- Usuario autenticado con permisos de edición en el proyecto

Postcondiciones
- Dependencias registradas en la base de datos (tabla intermedia RequerimientoCaso)
- Matriz de trazabilidad actualizada
- Relación visible en las vistas de detalle de requerimiento y caso de uso
- Registro de actividad en auditoría

Flujo Principal
1. El usuario accede al detalle de un requerimiento o caso de uso
2. Hace clic en "Relacionar casos de uso" o "Relacionar requerimientos"
3. El sistema muestra lista de elementos disponibles para vincular (solo del mismo proyecto)
4. El usuario selecciona uno o más elementos y confirma
5. El sistema valida que la relación no exista previamente
6. El sistema crea la relación en la tabla intermedia
7. El sistema actualiza la matriz de trazabilidad
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito y actualiza la vista

Flujos Alternativos
A1. Relación ya existente
- El sistema detecta que la dependencia ya existe y muestra mensaje informativo

A3. Proyecto sin elementos disponibles
- El sistema muestra mensaje: "No hay elementos disponibles para relacionar"

Reglas de Negocio
- RN-01: Solo se pueden vincular elementos del mismo proyecto
- RN-02: Un requerimiento puede estar vinculado a varios casos de uso y viceversa
- RN-03: No se permite duplicar relaciones

CU-08: Consultar historial de requerimientos

Descripción
Los usuarios con permisos adecuados pueden consultar el historial completo de cambios realizados sobre un requerimiento específico.

El historial incluye:
- Cambios de estado: Pendiente → En progreso → Completado
- Modificaciones de campos: nombre, descripción, tipo, prioridad
- Cambios en detalles específicos: campos tradicionales/ágiles
- Vinculaciones/desvinculaciones con casos de uso
- Adjuntos agregados o eliminados
- Comentarios registrados
- Metadatos: quién realizó el cambio, cuándo, desde qué IP (opcional)

Cada entrada del historial muestra:
- Fecha y hora del cambio
- Usuario que realizó la modificación
- Tipo de cambio (creación, edición, cambio de estado, etc.)
- Valores anteriores y nuevos (para campos modificados)
- Comentario opcional sobre el motivo del cambio

Este registro es fundamental para:
- Auditoría y cumplimiento normativo
- Trazabilidad de decisiones
- Resolución de conflictos
- Análisis retrospectivo

Actores
- Líder del proyecto (acceso completo al historial)
- Desarrollador/Analista (visualiza historial de requerimientos que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Requerimiento existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el requerimiento

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el requerimiento ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
   accion = CONSULTA_HISTORIAL
   detalles (JSON) = {requerimiento_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. El usuario selecciona un requerimiento específico
3. El usuario hace clic en "Ver detalle" o accede directamente a la vista de requerimiento
4. El sistema muestra la pantalla de detalle del requerimiento con pestañas/secciones:
   - Información actual
   - Casos de uso relacionados
   - Adjuntos
   - Comentarios
   - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del requerimiento:
   - Desde requerimientos_historicalrequerimiento (django-simple-history)
   - Incluye cambios en detalles: requerimientos_historicaldetallerequerimientotradicional o requerimientos_historicaldetallerequerimientoagil
   - Complementa con registros de auditoria_registroactividad para ver acciones específicas
7. El sistema combina datos de ambas fuentes:
   - django-simple-history: Snapshots completos de cada versión del requerimiento
   - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
   - Fecha y hora del cambio
   - Avatar/nombre del usuario que realizó el cambio
   - Icono según tipo de acción (creación, edición, cambio de estado, etc.)
   - Descripción del cambio en lenguaje natural
   - Botón "Ver detalles" para expandir
9. El usuario puede:
   - Revisar la lista completa de cambios
   - Expandir una entrada para ver detalles campo por campo
   - Comparar dos versiones específicas
   - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
11. El sistema muestra un modal/panel expandido con:
    - Tabla comparativa "Antes → Después"
    - Campos modificados destacados
    - Valores anteriores y nuevos
    - Comentario del usuario (si existe)
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

Flujos Alternativos

A1. Requerimiento sin historial (recién creado)
1. El sistema detecta solo la versión inicial
2. El sistema muestra mensaje: "Este requerimiento no tiene historial de cambios aún"
3. Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
1. El sistema detecta ausencia de módulo de auditoría
2. El sistema muestra mensaje: "El historial de cambios no está disponible en este momento"
3. Muestra solo: fecha de creación, creado por, fecha de última actualización
4. Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
1. El sistema detecta que participaciones.count() == 0
2. El sistema muestra mensaje:
   `
   ℹ️ Este proyecto no tiene participantes asignados.
   
   Para agregar participantes:
   1. Asigna un grupo al proyecto en "Editar Proyecto"
   2. O contacta al administrador para agregar usuarios manualmente
   
   [Volver al Dashboard]
   `
3. No se muestra la tabla de gestión
4. Fin del caso de uso

A4. Rol inválido seleccionado
1. El sistema recibe un rol_id no permitido en paso 12
2. El sistema valida: nuevo_rol not in roles_permitidos
3. El sistema omite ese cambio y muestra error:
   `
   ❌ El rol seleccionado para Juan Pérez no está permitido.
   Los demás cambios se guardaron correctamente.
   `
4. Los cambios válidos se guardan normalmente

A5. Usuario ya no es participante del proyecto
1. Entre paso 6 y paso 12, otro admin elimina al usuario del proyecto
2. El sistema intenta actualizar pero el usuario ya no existe en participantes
3. El sistema captura la excepción Usuario.DoesNotExist
4. El sistema omite ese cambio y continúa con los demás
5. Muestra advertencia: "Algunos usuarios ya no son participantes del proyecto."

4. El sistema muestra error: "Error al guardar los cambios. Intenta nuevamente."
5. Ningún rol es modificado

`python
@login_required
def asignar_metodologia(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)
    
    # Verificar que el usuario sea el líder
    if proyecto.lider != request.user:
        messages.error(request, "Solo el líder puede asignar la metodología.")
        return redirect("dashboards:lider_dashboard")
    
    # Verificar si se puede cambiar
    if not proyecto.necesita_metodologia() and not proyecto.puede_cambiar_metodologia():
        messages.error(request, "No puedes cambiar la metodología porque ya tiene requerimientos.")
        return redirect("dashboards:lider_dashboard")
    
    if request.method == "POST":
        metodologia = request.POST.get('metodologia')
        
        if metodologia in ['TRADICIONAL', 'AGIL']:
            proyecto.metodologia = metodologia
            proyecto.save()
            
            # Registrar en auditoría
            RegistroActividad.objects.create(
                usuario=request.user,
                accion='ASIGNACION_METODOLOGIA',
                detalles={
                    "proyecto_id": proyecto.id,
                    "proyecto_nombre": proyecto.nombre,
                    "metodologia": metodologia
                },
                ip_address=request.META.get('REMOTE_ADDR'),
                user_agent=request.META.get('HTTP_USER_AGENT')
            )
            
            metodologia_nombre = "Tradicional" if metodologia == "TRADICIONAL" else "Ágil"
            messages.success(request, f"Metodología '{metodologia_nombre}' asignada correctamente.")
            return redirect("dashboards:lider_dashboard")
        else:
            messages.error(request, "Metodología inválida seleccionada.")
    
    return render(request, "proyectos/asignar_metodologia.html", {
        "proyecto": proyecto,
        "puede_cambiar": proyecto.puede_cambiar_metodologia(),
        "necesita_metodologia": proyecto.necesita_metodologia(),
        "page_title": "Asignar Metodología"
    })

Descripción

Actores
- Analista
- Desarrollador
- Líder del proyecto

Precondiciones

- Usuario autenticado con permisos de edición en el proyecto

- Matriz de trazabilidad actualizada
- Relación visible en las vistas de detalle de requerimiento y caso de uso
- Registro de actividad en auditoría

CU-08: Consultar historial de requerimientos

Descripción
Los usuarios con permisos adecuados pueden consultar el historial completo de cambios realizados sobre un requerimiento específico.

El historial incluye:
- Cambios de estado: Pendiente → En progreso → Completado
- Modificaciones de campos: nombre, descripción, tipo, prioridad
- Cambios en detalles específicos: campos tradicionales/ágiles
- Vinculaciones/desvinculaciones con casos de uso
- Adjuntos agregados o eliminados
- Comentarios registrados
- Metadatos: quién realizó el cambio, cuándo, desde qué IP (opcional)

Cada entrada del historial muestra:
- Fecha y hora del cambio
- Usuario que realizó la modificación
- Tipo de cambio (creación, edición, cambio de estado, etc.)
- Valores anteriores y nuevos (para campos modificados)
- Comentario opcional sobre el motivo del cambio

Este registro es fundamental para:
- Auditoría y cumplimiento normativo
- Trazabilidad de decisiones
- Resolución de conflictos
- Análisis retrospectivo

Actores
- Líder del proyecto (acceso completo al historial)
- Desarrollador/Analista (visualiza historial de requerimientos que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Requerimiento existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el requerimiento

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el requerimiento ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
   accion = CONSULTA_HISTORIAL
   detalles (JSON) = {requerimiento_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. El usuario selecciona un requerimiento específico
3. El usuario hace clic en "Ver detalle" o accede directamente a la vista de requerimiento
4. El sistema muestra la pantalla de detalle del requerimiento con pestañas/secciones:
   - Información actual
   - Casos de uso relacionados
   - Adjuntos
   - Comentarios
   - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del requerimiento:
   - Desde requerimientos_historicalrequerimiento (django-simple-history)
   - Incluye cambios en detalles: requerimientos_historicaldetallerequerimientotradicional o requerimientos_historicaldetallerequerimientoagil
   - Complementa con registros de auditoria_registroactividad para ver acciones específicas
7. El sistema combina datos de ambas fuentes:
   - django-simple-history: Snapshots completos de cada versión del requerimiento
   - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
   - Fecha y hora del cambio
   - Avatar/nombre del usuario que realizó el cambio
   - Icono según tipo de acción (creación, edición, cambio de estado, etc.)
   - Descripción del cambio en lenguaje natural
   - Botón "Ver detalles" para expandir
9. El usuario puede:
   - Revisar la lista completa de cambios
   - Expandir una entrada para ver detalles campo por campo
   - Comparar dos versiones específicas
   - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
11. El sistema muestra un modal/panel expandido con:
    - Tabla comparativa "Antes → Después"
    - Campos modificados destacados
    - Valores anteriores y nuevos
    - Comentario del usuario (si existe)
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

Flujos Alternativos

A1. Requerimiento sin historial (recién creado)
1. El sistema detecta solo la versión inicial
2. El sistema muestra mensaje: "Este requerimiento no tiene historial de cambios aún"
3. Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
1. El sistema detecta ausencia de módulo de auditoría
2. El sistema muestra mensaje: "El historial de cambios no está disponible en este momento"
3. Muestra solo: fecha de creación, creado por, fecha de última actualización
4. Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
1. El sistema detecta que participaciones.count() == 0
2. El sistema muestra mensaje:
   `
   ℹ️ Este proyecto no tiene participantes asignados.
   
   Para agregar participantes:
   1. Asigna un grupo al proyecto en "Editar Proyecto"
   2. O contacta al administrador para agregar usuarios manualmente
   
   [Volver al Dashboard]
   `
3. No se muestra la tabla de gestión
4. Fin del caso de uso

A4. Rol inválido seleccionado
1. El sistema recibe un rol_id no permitido en paso 12
2. El sistema valida: nuevo_rol not in roles_permitidos
3. El sistema omite ese cambio y muestra error:
   `
   ❌ El rol seleccionado para Juan Pérez no está permitido.
   Los demás cambios se guardaron correctamente.
   `
4. Los cambios válidos se guardan normalmente

A5. Usuario ya no es participante del proyecto
1. Entre paso 6 y paso 12, otro admin elimina al usuario del proyecto
2. El sistema intenta actualizar pero el usuario ya no existe en participantes
3. El sistema captura la excepción Usuario.DoesNotExist
4. El sistema omite ese cambio y continúa con los demás
5. Muestra advertencia: "Algunos usuarios ya no son participantes del proyecto."

3. El sistema hace rollback de todos los cambios
4. El sistema muestra error: "Error al guardar los cambios. Intenta nuevamente."
5. Ningún rol es modificado
6. El formulario mantiene las selecciones del usuario

3. El líder confirma
4. El sistema redirige al dashboard sin guardar
5. Todos los roles permanecen sin cambios
6. Fin del caso de uso

- RN-02: La metodología es obligatoria para crear requerimientos
- RN-03: Valores válidos: 'TRADICIONAL' o 'AGIL' (campo CHOICES en modelo)

@login_required
def asignar_metodologia(request, proyecto_id):
    proyecto = get_object_or_404(Proyecto, id=proyecto_id)

            proyecto.save()

            RegistroActividad.objects.create(
                usuario=request.user,
                accion='ASIGNACION_METODOLOGIA',

                    "proyecto_nombre": proyecto.nombre,
                    "metodologia": metodologia
                },

            )
            
            metodologia_nombre = "Tradicional" if metodologia == "TRADICIONAL" else "Ágil"
            messages.success(request, f"Metodología '{metodologia_nombre}' asignada correctamente.")
            return redirect("dashboards:lider_dashboard")
        else:
            messages.error(request, "Metodología inválida seleccionada.")
    
    return render(request, "proyectos/asignar_metodologia.html", {
        "proyecto": proyecto,
        "puede_cambiar": proyecto.puede_cambiar_metodologia(),

    })

CU-11: Definir dependencias

Descripción
Permite vincular requerimientos y casos de uso entre sí para establecer relaciones de dependencia, trazabilidad y cobertura funcional. El objetivo es asegurar que cada requerimiento esté respaldado por uno o más casos de uso y que los casos de uso respondan a necesidades reales del proyecto.

Actores
- Analista
- Desarrollador
- Líder del proyecto

Precondiciones
- Proyecto existente con requerimientos y casos de uso registrados
- Usuario autenticado con permisos de edición en el proyecto

Postcondiciones
- Dependencias registradas en la base de datos (tabla intermedia RequerimientoCaso)
- Matriz de trazabilidad actualizada
- Relación visible en las vistas de detalle de requerimiento y caso de uso
- Registro de actividad en auditoría

Flujo Principal
1. El usuario accede al detalle de un requerimiento o caso de uso
2. Hace clic en "Relacionar casos de uso" o "Relacionar requerimientos"
3. El sistema muestra lista de elementos disponibles para vincular (solo del mismo proyecto)
4. El usuario selecciona uno o más elementos y confirma
5. El sistema valida que la relación no exista previamente
6. El sistema crea la relación en la tabla intermedia
7. El sistema actualiza la matriz de trazabilidad
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito y actualiza la vista

Flujos Alternativos
A1. Relación ya existente
- El sistema detecta que la dependencia ya existe y muestra mensaje informativo

A2. Usuario sin permisos
- El sistema bloquea la acción y muestra mensaje de error

A3. Proyecto sin elementos disponibles
- El sistema muestra mensaje: "No hay elementos disponibles para relacionar"

Reglas de Negocio
- RN-01: Solo se pueden vincular elementos del mismo proyecto
- RN-02: Un requerimiento puede estar vinculado a varios casos de uso y viceversa
- RN-03: No se permite duplicar relaciones
- RN-04: Las relaciones se reflejan en la matriz de trazabilidad
- RN-05: La acción se registra en auditoría con detalles completos

Estado de Implementación
✅ IMPLEMENTADO

- Actualización automática de matriz de trazabilidad

CU-08: Consultar historial de requerimientos

Descripción
Los usuarios con permisos adecuados pueden consultar el historial completo de cambios realizados sobre un requerimiento específico.

El historial incluye:
- Cambios de estado: Pendiente → En progreso → Completado
- Modificaciones de campos: nombre, descripción, tipo, prioridad
- Cambios en detalles específicos: campos tradicionales/ágiles
- Vinculaciones/desvinculaciones con casos de uso
- Adjuntos agregados o eliminados
- Comentarios registrados
- Metadatos: quién realizó el cambio, cuándo, desde qué IP (opcional)

Cada entrada del historial muestra:
- Fecha y hora del cambio
- Usuario que realizó la modificación
- Tipo de cambio (creación, edición, cambio de estado, etc.)
- Valores anteriores y nuevos (para campos modificados)
- Comentario opcional sobre el motivo del cambio

Este registro es fundamental para:
- Auditoría y cumplimiento normativo
- Trazabilidad de decisiones
- Resolución de conflictos
- Análisis retrospectivo

Actores
- Líder del proyecto (acceso completo al historial)
- Desarrollador/Analista (visualiza historial de requerimientos que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Requerimiento existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el requerimiento

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el requerimiento ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
   accion = CONSULTA_HISTORIAL
   detalles (JSON) = {requerimiento_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. El usuario selecciona un requerimiento específico
3. El usuario hace clic en "Ver detalle" o accede directamente a la vista de requerimiento
4. El sistema muestra la pantalla de detalle del requerimiento con pestañas/secciones:
   - Información actual
   - Casos de uso relacionados
   - Adjuntos
   - Comentarios
   - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del requerimiento:
   - Desde requerimientos_historicalrequerimiento (django-simple-history)
   - Incluye cambios en detalles: requerimientos_historicaldetallerequerimientotradicional o requerimientos_historicaldetallerequerimientoagil
   - Complementa con registros de auditoria_registroactividad para ver acciones específicas
7. El sistema combina datos de ambas fuentes:
   - django-simple-history: Snapshots completos de cada versión del requerimiento
   - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
   - Fecha y hora del cambio
   - Avatar/nombre del usuario que realizó el cambio
   - Icono según tipo de acción (creación, edición, cambio de estado, etc.)
   - Descripción del cambio en lenguaje natural
   - Botón "Ver detalles" para expandir
9. El usuario puede:
   - Revisar la lista completa de cambios
   - Expandir una entrada para ver detalles campo por campo
   - Comparar dos versiones específicas
   - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
11. El sistema muestra un modal/panel expandido con:
    - Tabla comparativa "Antes → Después"
    - Campos modificados destacados
    - Valores anteriores y nuevos
    - Comentario del usuario (si existe)
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

Flujos Alternativos

A1. Requerimiento sin historial (recién creado)
1. El sistema detecta solo la versión inicial
2. El sistema muestra mensaje: "Este requerimiento no tiene historial de cambios aún"
3. Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
1. El sistema detecta ausencia de módulo de auditoría
2. El sistema muestra mensaje: "El historial de cambios no está disponible en este momento"
3. Muestra solo: fecha de creación, creado por, fecha de última actualización
4. Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
1. El sistema detecta que participaciones.count() == 0
2. El sistema muestra mensaje:
   `
   ℹ️ Este proyecto no tiene participantes asignados.
   
   Para agregar participantes:
   1. Asigna un grupo al proyecto en "Editar Proyecto"
   2. O contacta al administrador para agregar usuarios manualmente
   
   [Volver al Dashboard]
   `
3. No se muestra la tabla de gestión
4. Fin del caso de uso

A4. Rol inválido seleccionado
1. El sistema recibe un rol_id no permitido en paso 12
2. El sistema valida: nuevo_rol not in roles_permitidos
3. El sistema omite ese cambio y muestra error:
   `
   ❌ El rol seleccionado para Juan Pérez no está permitido.
   Los demás cambios se guardaron correctamente.
   `
4. Los cambios válidos se guardan normalmente

A5. Usuario ya no es participante del proyecto
1. Entre paso 6 y paso 12, otro admin elimina al usuario del proyecto
2. El sistema intenta actualizar pero el usuario ya no existe en participantes
3. El sistema captura la excepción Usuario.DoesNotExist
4. El sistema omite ese cambio y continúa con los demás
5. Muestra advertencia: "Algunos usuarios ya no son participantes del proyecto."

A6. Error de base de datos al guardar
1. El sistema intenta guardar cambios en paso 12
2. Ocurre error de BD (connection error, constraint violation)
3. El sistema hace rollback de todos los cambios
4. El sistema muestra error: "Error al guardar los cambios. Intenta nuevamente."
5. Ningún rol es modificado
6. El formulario mantiene las selecciones del usuario

A7. Usuario cancela los cambios
1. El líder hace clic en "Cancelar" en paso 10
2. El sistema pregunta: "¿Deseas descartar los cambios?"
3. El líder confirma
4. El sistema redirige al dashboard sin guardar
5. Todos los roles permanecen sin cambios
6. Fin del caso de uso

Reglas de Negocio

- RN-01: Solo el líder del proyecto puede asignar o cambiar la metodología
- RN-02: La metodología es obligatoria para crear requerimientos
- RN-03: Valores válidos: 'TRADICIONAL' o 'AGIL' (campo CHOICES en modelo)
- RN-04: La metodología se puede cambiar SOLO si el proyecto no tiene requerimientos
- RN-05: Una vez creado el primer requerimiento, la metodología queda bloqueada
- RN-06: El cambio de metodología se registra en historial (django-simple-history)
- RN-07: El cambio se registra en auditoría con detalles completos

CU-11: Definir dependencias

Descripción
Permite vincular requerimientos y casos de uso entre sí para establecer relaciones de dependencia, trazabilidad y cobertura funcional. El objetivo es asegurar que cada requerimiento esté respaldado por uno o más casos de uso y que los casos de uso respondan a necesidades reales del proyecto.

Actores
- Analista
- Desarrollador
- Líder del proyecto

Precondiciones
- Proyecto existente con requerimientos y casos de uso registrados
- Usuario autenticado con permisos de edición en el proyecto

Postcondiciones
- Dependencias registradas en la base de datos (tabla intermedia RequerimientoCaso)
- Matriz de trazabilidad actualizada
- Relación visible en las vistas de detalle de requerimiento y caso de uso
- Registro de actividad en auditoría

Flujo Principal
1. El usuario accede al detalle de un requerimiento o caso de uso
2. Hace clic en "Relacionar casos de uso" o "Relacionar requerimientos"
3. El sistema muestra lista de elementos disponibles para vincular (solo del mismo proyecto)

6. El sistema crea la relación en la tabla intermedia
7. El sistema actualiza la matriz de trazabilidad
8. El sistema registra la acción en auditoría
9. El sistema muestra mensaje de éxito y actualiza la vista

Flujos Alternativos

CU-08: Consultar historial de requerimientos

Descripción
Los usuarios con permisos adecuados pueden consultar el historial completo de cambios realizados sobre un requerimiento específico.

El historial incluye:
- Cambios de estado: Pendiente → En progreso → Completado
- Modificaciones de campos: nombre, descripción, tipo, prioridad
- Cambios en detalles específicos: campos tradicionales/ágiles
- Vinculaciones/desvinculaciones con casos de uso
- Adjuntos agregados o eliminados
- Comentarios registrados
- Metadatos: quién realizó el cambio, cuándo, desde qué IP (opcional)

Cada entrada del historial muestra:
- Fecha y hora del cambio
- Usuario que realizó la modificación
- Tipo de cambio (creación, edición, cambio de estado, etc.)
- Valores anteriores y nuevos (para campos modificados)
- Comentario opcional sobre el motivo del cambio

Este registro es fundamental para:
- Auditoría y cumplimiento normativo
- Trazabilidad de decisiones
- Resolución de conflictos
- Análisis retrospectivo

Actores
- Líder del proyecto (acceso completo al historial)
- Desarrollador/Analista (visualiza historial de requerimientos que puede editar)
- Stakeholder (visualiza historial en modo lectura)
- Administrador (acceso completo a todos los historiales)

Precondiciones
- Usuario autenticado con permisos en el proyecto
- Requerimiento existente
- Sistema de auditoría habilitado (django-simple-history, django-reversion, o custom)
- Al menos un cambio registrado en el requerimiento

Postcondiciones
- Historial mostrado sin modificar datos
- Sin cambios en el requerimiento ni su historial
- Opcionalmente se registra consulta en auditoria_registroactividad con:
   accion = CONSULTA_HISTORIAL
   detalles (JSON) = {requerimiento_id, usuario_consultante}

Flujo Principal
1. El usuario accede a la lista de requerimientos del proyecto
2. El usuario selecciona un requerimiento específico
3. El usuario hace clic en "Ver detalle" o accede directamente a la vista de requerimiento
4. El sistema muestra la pantalla de detalle del requerimiento con pestañas/secciones:
   - Información actual
   - Casos de uso relacionados
   - Adjuntos
   - Comentarios
   - Historial de cambios
5. El usuario hace clic en la pestaña "Historial"
6. El sistema recupera todas las versiones históricas del requerimiento:
   - Desde requerimientos_historicalrequerimiento (django-simple-history)
   - Incluye cambios en detalles: requerimientos_historicaldetallerequerimientotradicional o requerimientos_historicaldetallerequerimientoagil
   - Complementa con registros de auditoria_registroactividad para ver acciones específicas
7. El sistema combina datos de ambas fuentes:
   - django-simple-history: Snapshots completos de cada versión del requerimiento
   - auditoria_registroactividad: Acciones contextuales (quién, cuándo, desde dónde, por qué)
8. El sistema muestra una línea de tiempo cronológica inversa (más reciente primero):
   - Fecha y hora del cambio
   - Avatar/nombre del usuario que realizó el cambio
   - Icono según tipo de acción (creación, edición, cambio de estado, etc.)
   - Descripción del cambio en lenguaje natural
   - Botón "Ver detalles" para expandir
9. El usuario puede:
   - Revisar la lista completa de cambios
   - Expandir una entrada para ver detalles campo por campo
   - Comparar dos versiones específicas
   - Filtrar por tipo de cambio o rango de fechas
10. El usuario hace clic en "Ver detalles" de una entrada
11. El sistema muestra un modal/panel expandido con:
    - Tabla comparativa "Antes → Después"
    - Campos modificados destacados
    - Valores anteriores y nuevos
    - Comentario del usuario (si existe)
12. El usuario revisa los detalles
13. El usuario cierra el modal y puede continuar navegando el historial

Flujos Alternativos

A1. Requerimiento sin historial (recién creado)
1. El sistema detecta solo la versión inicial
2. El sistema muestra mensaje: "Este requerimiento no tiene historial de cambios aún"
3. Muestra solo la entrada de creación con fecha, hora y creador

A2. Sistema de historial no implementado
1. El sistema detecta ausencia de módulo de auditoría
2. El sistema muestra mensaje: "El historial de cambios no está disponible en este momento"
3. Muestra solo: fecha de creación, creado por, fecha de última actualización
4. Sugiere contactar al administrador para habilitar auditoría

A3. Historial muy extenso (>100 cambios)
1. El sistema detecta que participaciones.count() == 0
2. El sistema muestra mensaje:
   `
   ℹ️ Este proyecto no tiene participantes asignados.
   
   Para agregar participantes:
   1. Asigna un grupo al proyecto en "Editar Proyecto"
   2. O contacta al administrador para agregar usuarios manualmente
   
   [Volver al Dashboard]
   `
3. No se muestra la tabla de gestión
4. Fin del caso de uso

A4. Rol inválido seleccionado
1. El sistema recibe un rol_id no permitido en paso 12
2. El sistema valida: nuevo_rol not in roles_permitidos
3. El sistema omite ese cambio y muestra error:
   `
   ❌ El rol seleccionado para Juan Pérez no está permitido.
   Los demás cambios se guardaron correctamente.
   `
4. Los cambios válidos se guardan normalmente

A5. Usuario ya no es participante del proyecto
1. Entre paso 6 y paso 12, otro admin elimina al usuario del proyecto
2. El sistema intenta actualizar pero el usuario ya no existe en participantes
3. El sistema captura la excepción Usuario.DoesNotExist
4. El sistema omite ese cambio y continúa con los demás
5. Muestra advertencia: "Algunos usuarios ya no son participantes del proyecto."

A6. Error de base de datos al guardar
1. El sistema intenta guardar cambios en paso 12
2. Ocurre error de BD (connection error, constraint violation)
3. El sistema hace rollback de todos los cambios
4. El sistema muestra error: "Error al guardar los cambios. Intenta nuevamente."
5. Ningún rol es modificado
6. El formulario mantiene las selecciones del usuario

A7. Usuario cancela los cambios
1. El líder hace clic en "Cancelar" en paso 10
2. El sistema pregunta: "¿Deseas descartar los cambios?"
3. El líder confirma
4. El sistema redirige al dashboard sin guardar
5. Todos los roles permanecen sin cambios
6. Fin del caso de uso

Reglas de Negocio

- RN-01: Solo el líder del proyecto puede asignar o cambiar la metodología
- RN-02: La metodología es obligatoria para crear requerimientos
- RN-03: Valores válidos: 'TRADICIONAL' o 'AGIL' (campo CHOICES en modelo)
- RN-04: La metodología se puede cambiar SOLO si el proyecto no tiene requerimientos
- RN-05: Una vez creado el primer requerimiento, la metodología queda bloqueada
- RN-06: El cambio de metodología se registra en historial (django-simple-history)
- RN-07: El cambio se registra en auditoría con detalles completos
- RN-08: Un proyecto sin metodología muestra advertencia en el dashboard
- RN-09: No se pueden crear requerimientos sin metodología asignada previamente

    max_length=20, 
    choices=METODOLOGIAS, 
    null=True, 
    blank=True
)

def puede_cambiar_metodologia(self):
    """Solo se puede cambiar si NO hay requerimientos"""
    return not self.requerimientos.exists()

def necesita_metodologia(self):
    """Verifica si necesita asignar metodología"""
    return self.metodologia is None or self.metodologia == ''

@login_required
def lider_matriz(request, proyecto_id):
    """Vista de matriz de trazabilidad CORRECTA usando relaciones reales."""
    proyecto = get_object_or_404(Proyecto, pk=proyecto_id)
    
    # Verificar permisos
    if not request.user.tiene_permiso_lectura(proyecto):
        messages.error(request, "No tienes permisos para ver este proyecto")
        return redirect('proyectos:lista')
    
    # ✅ CORRECTO: Obtener datos con relaciones
    requerimientos = Requerimiento.objects.filter(
        proyecto=proyecto
    ).prefetch_related('casos_relacionados')
    
    casos = CasoDeUso.objects.filter(
        proyecto=proyecto
    ).prefetch_related('requerimientos_relacionados')
    
    # ✅ Construir matriz usando relaciones REALES de la tabla intermedia
    matriz_data = []
    for req in requerimientos:
        casos_vinculados = req.casos_relacionados.all()  # Usa la relación M2M real
        matriz_data.append({
            'requerimiento': req,
            'casos_vinculados': casos_vinculados,
            'tiene_casos': casos_vinculados.exists(),
            'es_must_have': (
                req.detalle_tradicional.prioridad == 'MUST' 
                if req.detalle_tradicional else False
            )
        })
    
    # Calcular estadísticas
    total_reqs = requerimientos.count()
    total_casos = casos.count()
    
    # Requerimientos con al menos un caso
    reqs_con_casos = requerimientos.annotate(
        num_casos=Count('casos_relacionados')
    ).filter(num_casos__gt=0).count()
    
    # Casos con al menos un requerimiento
    casos_con_reqs = casos.annotate(
        num_reqs=Count('requerimientos_relacionados')
    ).filter(num_reqs__gt=0).count()
    
    # Huérfanos
    reqs_huerfanos = requerimientos.annotate(
        num_casos=Count('casos_relacionados')
    ).filter(num_casos=0)
    
    casos_huerfanos = casos.annotate(
        num_reqs=Count('requerimientos_relacionados')
    ).filter(num_reqs=0)
    
    # Must Have sin casos (CRÍTICO)
    reqs_must_sin_casos = requerimientos.filter(
        detalle_tradicional__prioridad='MUST'
    ).annotate(
        num_casos=Count('casos_relacionados')
    ).filter(num_casos=0)
    
    # Porcentajes de cobertura
    cobertura_reqs = (reqs_con_casos / total_reqs  100) if total_reqs > 0 else 0
    cobertura_casos = (casos_con_reqs / total_casos  100) if total_casos > 0 else 0
    
    # Nivel de alerta
    if reqs_must_sin_casos.exists():
        nivel_alerta = 'danger'  # Crítico: Must Have sin casos
    elif cobertura_reqs < 80:
        nivel_alerta = 'warning'  # Advertencia: baja cobertura
    else:
        nivel_alerta = 'success'  # OK
    
    return render(request, 'dashboards/lider_matriz.html', {
        'proyecto': proyecto,
        'requerimientos': requerimientos,
        'casos': casos,
        'matriz_data': matriz_data,
        'total_reqs': total_reqs,
        'total_casos': total_casos,
        'reqs_con_casos': reqs_con_casos,
        'casos_con_reqs': casos_con_reqs,
        'reqs_huerfanos': reqs_huerfanos,
        'casos_huerfanos': casos_huerfanos,
        'reqs_must_sin_casos': reqs_must_sin_casos,
        'cobertura_reqs': round(cobertura_reqs, 1),
        'cobertura_casos': round(cobertura_casos, 1),
        'nivel_alerta': nivel_alerta,
    })
`

function getCookie(name) {
    let cookieValue = null;
    if (document.cookie && document.cookie !== '') {
        const cookies = document.cookie.split(';');
        for (let i = 0; i < cookies.length; i++) {
            const cookie = cookies[i].trim();
            if (cookie.substring(0, name.length + 1) === (name + '=')) {
                cookieValue = decodeURIComponent(cookie.substring(name.length + 1));
                break;
            }
        }
    }
    return cookieValue;
}
