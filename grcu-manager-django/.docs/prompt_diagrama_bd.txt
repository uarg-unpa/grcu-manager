========================================
TABLAS PRINCIPALES Y SUS CAMPOS
========================================

1. accounts_usuario (Usuario - hereda de AbstractUser)
- id: BIGINT (PK, Auto-incremento)
- password: VARCHAR(128) - Hash de contraseña para admin/superusers

- is_superuser: BOOLEAN - Indica si es superusuario
- first_name: VARCHAR(150) - Nombre (campo Django)
- last_name: VARCHAR(150) - Apellido (campo Django)
- is_staff: BOOLEAN - Puede acceder al admin de Django
- is_active: BOOLEAN - Usuario activo en el sistema
- date_joined: TIMESTAMP - Fecha de registro
- email: VARCHAR(254) (UNIQUE, INDEX) - Email para autenticación OAuth2
- nombre: VARCHAR(255) (INDEX) - Nombre completo del usuario
- avatar: VARCHAR(200) (NULL) - URL del avatar de Google OAuth2
- username: VARCHAR(150) (NULL) - No usado, autenticación por email

2. roles_rol (Rol)
- id: BIGINT (PK, Auto-incremento)
- nombre: VARCHAR(50) (UNIQUE) - Nombre del rol (Admin, Líder, Desarrollador, etc.)

6. proyectos_participacionproyecto (ParticipacionProyecto - Tabla intermedia)

INSTRUCCIONES PARA GENERAR EL DIAGRAMA

Formato Preferido
Utiliza Mermaid.js para generar el diagrama ERD (Entity Relationship Diagram).

Estructura del Diagrama
1. Entidades Principales (rectángulos azules):
   - accounts_usuario, roles_rol, permisos_permiso, grupos_grupo, proyectos_proyecto, requerimientos_requerimiento, casos_de_uso_casodeuso, auditoria_registroactividad

2. Entidades de Detalle (rectángulos verdes):
   - requerimientos_detallerequerimientotradicional, requerimientos_detallerequerimientoagil
   - casos_de_uso_detallecasodeusotradicional, casos_de_uso_detallecasodeusoagil
   - proyectos_participacionproyecto, requerimientos_requerimientocaso

3. Relaciones:
   - One-to-One: Línea continua con |o--||o
   - One-to-Many: Línea continua con ||--o{
   - Many-to-Many: Línea discontinua con }o--o{

Campos a Mostrar
- **Campos PK**: En negrita con *
- **Campos FK**: Con sufijo `_id`
- **Campos únicos**: Con subrayado
- **Campos opcionales**: Con `(NULL)` al final

Agrupación Lógica

- **Grupo de Organización**: grupos_grupo, proyectos_proyecto, proyectos_participacionproyecto

========================================
CONSIDERACIONES ESPECIALES DEL SISTEMA
========================================

**Autenticación y Seguridad:**
- Usuario hereda de AbstractUser de Django (incluye campos password, is_staff, is_superuser, etc.)
- Autenticación principal vía Google OAuth2 (campo avatar almacena URL de foto)
- Campo password usado solo para superusers que acceden al admin de Django
- Campo username=NULL, autenticación por email únicamente

**Metodología de Desarrollo:**
- Proyectos pueden ser TRADICIONAL o AGIL
- Requerimientos y Casos de Uso tienen detalles específicos según metodología
- Relación OneToOne entre entidad principal y sus detalles (detalle_tradicional_id / detalle_agil_id)

**Gestión de Archivos:**
- ImageField usado para logos (grupos/proyectos) y adjuntos (requerimientos/casos de uso)
- Rutas de almacenamiento: grupos/logos/, proyectos/logos/, requerimientos/imagenes/, casos_de_uso/imagenes/

**Tracking de Cambios:**
- django-simple-history implementado en Proyecto, Requerimiento y CasoDeUso
- Tablas Historical almacenan snapshots de cada cambio con history_type (+/-/~)
- history_user_id registra quién hizo el cambio
- history_date registra cuándo se hizo

**Constraints y Validaciones:**
- UNIQUE en ParticipacionProyecto (usuario, proyecto) - Un usuario un rol por proyecto
- UNIQUE en RequerimientoCaso (requerimiento, caso_de_uso) - Evita duplicados
- PROTECT en rol_id de ParticipacionProyecto - No se puede borrar rol si está en uso
- CASCADE en relaciones Proyecto -> Requerimiento/CasoDeUso - Borrado en cascada
- SET_NULL en relaciones Usuario -> Entidades - Preserva datos si se borra usuario

**Auditoría del Sistema:**
- RegistroActividad con campo JSON para detalles flexibles
- Múltiples índices para consultas eficientes (fecha DESC, usuario+fecha, acción)
- Campo INET para almacenar direcciones IP
- Acciones predefinidas: LOGIN, LOGOUT, CREATE_USER, UPDATE_USER, DELETE_USER, CHANGE_ROLE, etc.

**Soft Deletes:**
- Campo 'activo' en Grupo y Proyecto para eliminación lógica
- No se implementan hard deletes, se desactivan las entidades

**Relaciones Many-to-Many:**
- Usuario <-> Rol (tabla accounts_usuario_roles)
- Grupo <-> Usuario integrantes (tabla grupos_grupo_integrantes)
- Rol <-> Permiso (tabla roles_rol_permisos)
- Requerimiento <-> CasoDeUso (dos tablas: requerimientos_requerimiento_casos_relacionados y requerimientos_requerimientocaso)
- Proyecto <-> Usuario participantes (through model proyectos_participacionproyecto con constraint UNIQUE)
